## 2026-10-27 — Parity phase 3a: lifecycle, permissions, findings, comments, archive

- Three new application statuses: `revisions_requested`, `returned` and `archived`. A Data Steward returns a case (terminal, typed reason code) or advances it to review while no current, unwaived blocking finding stands in the way; a Permit Reviewer asks for revisions with a typed reason code and a message the applicant reads; an applicant answers and resubmits (atomic, stales the evaluation, the recommendation and the decision, keeps the first submission date, returns to intake); a City Administrator archives and restores.
- The archive guard is a service-level rule: the API revision path, the document store, the evaluation, both agents, the recommendation confirm/revert paths, the five parcel operations, the finance paths, the portal upload and resubmission, the decision and reconfirmation paths and the issuance path all refuse an archived case. Only a version-checked restore reactivates it, and a restore never revives a stale approval.
- Reason codes carry a type (`return`, `denial`, `waiver`, `revision`, `archive`) and are validated in the service that acts on the case. The five shipped codes are backfilled explicitly in migration 0006; the seeded set grows to twelve fictional ACME codes. A denial needs a denial reason code on every decision path.
- Findings gained `wrong_type` and `fee` with producers in the intake graph, and a state (`current` / `resolved` / `superseded`). A Data Steward may waive a current waivable finding with a reason code and a free-text reason; a waiver never clears a deterministic rule failure or an identity, credential, finance or parcel-clearance check, and every decision snapshots the waivers that applied.
- A real comment model replaces the phase 2 workaround that built "Messages from the City" out of the findings. A comment is visible to the applicant or internal, the server enforces that on every surface, and the audit record carries the comment id and visibility but never the text.
- Priority (`normal` / `high`) and owner are routing metadata. The owner grants nothing and never adds a selectable persona; the eligible owners are the active people eligible for the stage of the case.
