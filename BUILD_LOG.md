## 2026-10-27 — Parity phase 3a: lifecycle, permissions, findings, comments, archive

- Three new application statuses: `revisions_requested`, `returned` and `archived`. A Data Steward returns a case (terminal, typed reason code) or advances it to review while no current, unwaived blocking finding stands in the way; a Permit Reviewer asks for revisions with a typed reason code and a message the applicant reads; an applicant answers and resubmits (atomic, stales the evaluation, the recommendation and the decision, keeps the first submission date, returns to intake); a City Administrator archives and restores.
- The archive guard is a service-level rule: the API revision path, the document store, the evaluation, both agents, the recommendation confirm/revert paths, the five parcel operations, the finance paths, the portal upload and resubmission, the decision and reconfirmation paths and the issuance path all refuse an archived case. Only a version-checked restore reactivates it, and a restore never revives a stale approval.
- Reason codes carry a type (`return`, `denial`, `waiver`, `revision`, `archive`) and are validated in the service that acts on the case. The five shipped codes are backfilled explicitly in migration 0006; the seeded set grows to twelve fictional ACME codes. A denial needs a denial reason code on every decision path.
- Findings gained `wrong_type` and `fee` with producers in the intake graph, and a state (`current` / `resolved` / `superseded`). A Data Steward may waive a current waivable finding with a reason code and a free-text reason; a waiver never clears a deterministic rule failure or an identity, credential, finance or parcel-clearance check, and every decision snapshots the waivers that applied.
- A real comment model replaces the phase 2 workaround that built "Messages from the City" out of the findings. A comment is visible to the applicant or internal, the server enforces that on every surface, and the audit record carries the comment id and visibility but never the text.
- Priority (`normal` / `high`) and owner are routing metadata. The owner grants nothing and never adds a selectable persona; the eligible owners are the active people eligible for the stage of the case.

## 2026-10-28 — Parity phase 3 chat 1: the applicant help assistant, deterministic

- The applicant help assistant answers an applicant's questions about the ACME permit process, the rules that apply to their project and their own application. It is offered on the chooser (`/apply`), on the application form (`/apply/<type>`) and on the tracker (`/apply/track?ref=…`); no other persona may open it.
- **The answer is deterministic in this part of the work.** There is no model call anywhere in the path: the answer is a stable ranking over a source bundle the server builds, and it quotes the matching passages. The Muse path, the replay fixtures and the live switch arrive with the next run of the chat part.
- The **source bundle** is built from the *published* rule versions in force at the basis date and from the stored permit-type configuration, never from the catalogue file (which carries drafts). A rule is rendered with its **applicability**, its **operator**, its **threshold** and its **conditions**, and the message of a rule is rendered under "If the rule is not met", so a violation is never presented as an unconditional fact. The basis date is the application's first submission time for the rules of that case and the server's own time for general guidance.
- The bundle also holds the applicant's **own** case: its status, the current findings with their "you must" line, the comments written for the applicant and the next step open to them. An internal note never enters it, another applicant's record never enters it, and the bundle is refused by the same truth guard the model payloads use.
- The answer is labelled **"Matching ACME rule text (not an AI answer)"** and a question that matches nothing gets an explicit **no-match**, never a guess. A limit is never an exemption: the answer quotes the rule with the applicability it has, so the 6 ft side-and-rear limit is shown beside the 4 ft front-yard limit.
- The panel shows the configured **service target** and the current **backlog of the review area** as two separate figures, each with its own definition and the time it was read. They are never added together, no completion date is computed and no queue position is claimed.
- The conversation belongs to the applicant who opened it. Asking needs the new `applicant.help.ask` grant, the CSRF token and a **mandatory expected version**; **Ask the City** needs the new `applicant.help.escalate` grant and the same mandatory version, and it creates a help request, which is the only route by which a member of the City sees the applicant's question. The rate limit is 10 questions per session per 10 minutes, the session is stored as a hash, and a question is at most 1,000 characters.
- The **audit record** of a question carries the identifiers and the outcome of the turn. It never carries the text of the question.
- The help question is a **form of its own**, never part of the application form. On the application form the answer opens in a **separate browsing context** (`/apply/help/panel`), so the fields and the files the applicant typed stay intact; with JavaScript the answer is rendered in place instead.
- The server-only setting `applicant_assist_live_enabled` is **off by default**; a credential alone never enables a live answer for an applicant.
- Migration 0008 carries the three new tables (`help_conversations`, `help_turns`, `help_requests`); the migration head tests moved from `0007` to `0008`.
- Execution: the part was built as one unit and committed together, because the source bundle, the matcher, the service, the panel and the three placements are one feature; the model path, the escalation prompt and the Administrator's answer service are the next two runs of this part.
